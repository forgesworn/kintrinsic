# Local network delivery: platform notes

Facts checked against official documentation and AOSP or Chromium source on 2026-10-25, used by [the design](local-network-design.md). "Not confirmed" means no official source was found.

## 1. NsdManager (API 29-36)
- INTERNET is the only permission NsdService enforces on connect (AOSP, NsdService.java `connect()`):
  `mContext.enforceCallingOrSelfPermission(android.Manifest.permission.INTERNET, "NsdService");`
  https://android.googlesource.com/platform/packages/modules/Connectivity/+/refs/heads/main/service-t/src/com/android/server/NsdService.java
- CHANGE_WIFI_MULTICAST_STATE is only needed if the APP itself takes a MulticastLock (normal permission):
  "Allows applications to enter Wi-Fi Multicast mode. Protection level: normal"
  https://developer.android.com/reference/android/Manifest.permission
- Multicast lock rule (official): "Before T extensions 7 (Android 12 and below devices, and Android 13 devices that have not received the T extensions 7 update): Apps must manually acquire a WifiManager.MulticastLock to receive mDNS packets, even when the app is in the foreground. Starting from T extensions 7: The system automatically manages multicast reception for apps in the foreground. Background apps should still avoid taking the lock unless absolutely necessary"
  https://developer.android.com/reference/android/net/nsd/NsdManager
- GOTCHA for the ward (FGS, not "foreground"): the system's auto-lock only counts UIDs with importance <= IMPORTANCE_FOREGROUND (100); AOSP:
  `DEFAULT_RUNNING_APP_ACTIVE_IMPORTANCE_CUTOFF = ActivityManager.RunningAppProcessInfo.IMPORTANCE_FOREGROUND;` and `mRunningAppActiveUids` gates `getMulticastLockNeededUid()`. A foreground-SERVICE-only process is IMPORTANCE_FOREGROUND_SERVICE = 125 (> 100), so it is NOT "active": no auto lock, Wi-Fi APF may filter inbound mDNS multicast while the screen is off. Mitigation: hold own MulticastLock (needs CHANGE_WIFI_MULTICAST_STATE). Inference from source, not stated in docs.
  https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/app/ActivityManager.java ("IMPORTANCE_FOREGROUND = 100", "IMPORTANCE_FOREGROUND_SERVICE = 125")
- resolveService deprecated API 34: "This method was deprecated in API level 34. the returned ServiceInfo may get stale at any time after resolution ... Prefer using registerServiceInfoCallback(DiscoveryRequest, Executor, ServiceInfoCallback)"
  https://developer.android.com/reference/android/net/nsd/NsdManager
- registerServiceInfoCallback(DiscoveryRequest,...): "available starting from 'T extensions 22' (which covers all Android 14+ devices), combines discovery and resolution into a single operation." Older: discoverServices + registerServiceInfoCallback(NsdServiceInfo,..)/resolveService. (same page)
- Service type rules. AOSP validator (NsdService.parseTypeAndSubtype): "Each label is up to 63 characters and must start with an underscore ... The last label must be _tcp or _udp." Format "_name._tcp". The 15-char limit is RFC 6763/6335, not enforced by NSD code: "no more than fifteen characters long (not counting the mandatory underscore)". `_kintrinsic._tcp` = 10 chars + underscore: OK.
  https://www.rfc-editor.org/rfc/rfc6763.txt (s.7.2); AOSP link above.

## 2. Local network protection / ACCESS_LOCAL_NETWORK
- Page last updated 2026-10-02. "During Android 16, this permission is an opt-in feature which means only the apps that opt-in will be affected." "Starting in Android 17, local network protections are mandatory and enforced for apps targeting Android 17 or higher."
  https://developer.android.com/privacy-and-security/local-network-permission
- Permission: android.permission.ACCESS_LOCAL_NETWORK, API 37, dangerous, in NEARBY_DEVICES group. "Required to be able to advertise and connect to local network devices." (Manifest.permission ref above). Android 16 opt-in used NEARBY_WIFI_DEVICES temporarily.
- Trigger: "The ACCESS_LOCAL_NETWORK permission is required only if your app targets Android 17 (SDK 37) or higher. If your app targets SDK 36 or lower, local network access is implicitly granted using the INTERNET permission." => targetSdk 35 is NOT enforced; bumping to 37 later blocks LAN by default.
- Coverage (targetSdk>=37): "Accepting an incoming TCP connection: yes"; "Making an outgoing TCP connection: yes"; UDP unicast/multicast/broadcast send+receive: yes; "they apply to all networking APIs. This includes sockets created in the platform or managed code ..." Also lists raw mDNS/SSDP and "framework-level classes ... for example, NsdManager". Android 16 opt-in only: NsdManager "aren't affected during the opt-in."
- Exceptions: DNS server on LAN at port 53; WebView "inherit permission state from the host app"; NsdManager picker path (DiscoveryRequest.FLAG_SHOW_PICKER) grants per-service access without the permission.
- NsdManager ref: "Starting with API 37, access to the local network is restricted. Applications targeting API 37 or higher generally require the Manifest.permission.ACCESS_LOCAL_NETWORK permission" and registerService "always requires the ACCESS_LOCAL_NETWORK permission". https://developer.android.com/reference/android/net/nsd/NsdManager
- Device Owner exemption: not confirmed (no mention found).

## 3. Doze / App Standby / foreground service
- Public doc does NOT exempt FGS from Doze: "Doze restrictions: Suspends network access. Ignores wake locks." and the FGS bullet is under App Standby only: "The app has a process currently in the foreground, either as an activity or foreground service". https://developer.android.com/training/monitoring-device-state/doze-standby
- AOSP behaviour (authoritative, contradicts a naive reading of the doc): NPMS adds every uid with `isProcStateAllowedWhileIdleOrPowerSaveMode` to the dozable-chain ALLOW list. NetworkPolicyManager: `return procState <= FOREGROUND_THRESHOLD_STATE || (capability & PROCESS_CAPABILITY_POWER_RESTRICTED_NETWORK) != 0;` with `FOREGROUND_THRESHOLD_STATE = ActivityManager.PROCESS_STATE_BOUND_FOREGROUND_SERVICE` (ordering: TOP < BOUND_TOP < FOREGROUND_SERVICE < BOUND_FOREGROUND_SERVICE). `getDefaultProcessNetworkCapabilities` also grants POWER_RESTRICTED_NETWORK for FOREGROUND_SERVICE. => a running FGS keeps inbound+outbound network in Doze (and Battery Saver).
  https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/net/NetworkPolicyManager.java ; .../services/core/java/com/android/server/net/NetworkPolicyManagerService.java (`updateRulesForAllowlistedPowerSaveUL`)
- Wake locks in Doze: PowerManagerService disables partial wake locks only if the uid is not allowlisted AND `state.mProcState > PROCESS_STATE_BOUND_FOREGROUND_SERVICE`, so an FGS process may hold a partial wake lock. (frameworks/base/.../power/PowerManagerService.java `setWakeLockDisabledStateLocked`)
- Low Power Standby (Android 14+, opt-in, screen off): STRICTER, FGS not exempt: `isProcStateAllowedWhileInLowPowerStandby: uidState.procState <= TOP_THRESHOLD_STATE` (BOUND_TOP). PowerManager docs: "apps (including apps running foreground services) are subject to additional restrictions while the device is non-interactive" ; `isExemptFromLowPowerStandby()` API 34. https://developer.android.com/reference/android/os/PowerManager
- Do incoming TCP packets on an established connection wake the device from Doze? NOT CONFIRMED in any official doc (no statement about WoWLAN/kernel wake). Doc only lists exits: "When the user wakes the device by moving it, turning on the screen, or connecting a charger" / setAlarmClock. Treat inbound wake as unreliable; use a partial wake lock + keepalive or accept maintenance-window latency.

## 4. Cleartext policy scope
- android:usesCleartextTraffic: "there's no expectation that the Socket API honors this flag, because it can't determine whether its traffic is in cleartext." "platform components, for example, HTTP and FTP stacks, DownloadManager, and MediaPlayer, refuse the app's requests". "WebView honors this attribute for applications targeting API level 26 and higher." Attribute "will be ignored for apps targeting API levels 38 and above" (use NSC).
  https://developer.android.com/guide/topics/manifest/application-element
- Network Security Config is destination-scoped, cleartext "using the unencrypted HTTP protocol"; default off from API 28. https://developer.android.com/privacy-and-security/security-config
- NDK/Rust sockets: not mentioned anywhere; by the above they are unaffected (inference). Note: if the ward ever uses OkHttp/HttpURLConnection/WebView for LAN, cleartext DOES apply.

## 5. Browsers
- Chrome LNA timeline (official release notes): 142 (stable 2025-10-28; Android, ChromeOS, Linux, macOS, Windows) "restricts the ability to make requests to the user's local network, gated behind a permission prompt" https://developer.chrome.com/release-notes/142 ; 145 (2026-02-10) split into `local-network` and `loopback-network` ("local-network-access" kept as alias) https://developer.chrome.com/release-notes/145 ; 147 (2026-04-07) "WebSockets connections to local addresses now trigger permission prompts." (also WebTransport) https://developer.chrome.com/release-notes/147
- Original post (updated 2025-09-29): "The ability to request this permission is restricted to secure contexts." Covers loopback and local. https://developer.chrome.com/blog/local-network-access
- WICG spec (draft, 7 Aug 2026): "WebSockets connections should be subject to the same local network access permission requirements"; WebSocket has no `targetAddressSpace` equivalent for fetch. https://wicg.github.io/local-network-access/
- ws:// from https page, Chromium source (mixed_content_checker.cc): WebSocket is mixed content unless "potentially trustworthy" (`IsInsecureUrl: |url| is mixed content if it is not a potentially trustworthy URL`). Exception: `IsWebSocketLNAAllowed` skips the mixed-content block when URL is a local/loopback IP literal and `kLocalNetworkAccessChecksWebSockets` (BASE_FEATURE_ENABLED_BY_DEFAULT in services/network/public/cpp/features.cc), leaving the LNA permission check. Hostnames (e.g. foo.local resolving to LAN) are blocked before resolution. => https PWA -> ws://192.168.x.y works only for IP literals AND after user grants the prompt; wss:// to a LAN IP needs a trusted cert (not practical).
  https://chromium.googlesource.com/chromium/src/+/refs/heads/main/third_party/blink/renderer/core/loader/mixed_content_checker.cc
- ws://localhost / 127.0.0.1: Secure Contexts: "If origin's host matches one of the CIDR notations 127.0.0.0/8 or ::1/128" => potentially trustworthy (also "localhost", "*.localhost"), so not mixed content in Chrome; still needs the `loopback-network` prompt from Chrome 147. https://w3c.github.io/webappsec-secure-contexts/ ; MDN: "content accessed from loopback addresses such as http://127.0.0.1/ or http://localhost/" is treated as secure. Safari/Firefox behaviour for ws://127.0.0.1 from https: not confirmed.
- Android System WebView: blink-dev LNA WebSockets post: "This is unsupported on WebView for the same reasons that Local Network Access is unsupported on WebView." (Chrome's prompt not applied; mixed-content rules still apply.) Android 17 doc: WebView traffic "inherit[s] permission state from the host app". https://groups.google.com/a/chromium.org/g/blink-dev/c/4gx2y5jPGbU
- Discovery APIs: no web-page mDNS/DNS-SD API found (only extension/app `chrome.mdns`, https://developer.chrome.com/docs/apps/reference/mdns). Not confirmed that any shipped web API exists.
- Direct Sockets (TCPSocket/TCPServerSocket/UDPSocket + multicast): "restricted to Isolated Web Apps (IWAs)", needs `direct-sockets` permissions policy; multicast needs `direct-sockets-multicast`. https://developer.chrome.com/docs/iwa/direct-sockets ; explainer "planned to be available only in Isolated Web Apps" https://github.com/WICG/direct-sockets/blob/main/docs/explainer.md . blink-dev PSA: `direct-sockets-private` -> `local-network`/`loopback-network` policies, "No. Only ChromeOS", Chrome 151: https://groups.google.com/a/chromium.org/g/blink-dev/c/5cSZjgnJelk/m/K56ic8m_AgAJ . Unusable from a normal PWA or Android.

## 6. avahi D-Bus (bus name org.freedesktop.Avahi, path /)
- Source of truth: avahi-daemon/org.freedesktop.Avahi.Server.xml (master) https://raw.githubusercontent.com/avahi/avahi/master/avahi-daemon/org.freedesktop.Avahi.Server.xml
- Interface `org.freedesktop.Avahi.Server`: `ServiceBrowserNew(i interface, i protocol, s type, s domain, u flags) -> o path` (signals can be emitted before client can subscribe: the race; documented in no official doc I found, the Prepare/Start design is the fix).
- Interface `org.freedesktop.Avahi.Server2` (added by commit 725e9b84 "Added new Avahi Server DBus Interface (org.freedesktop.Avahi.Server2) and incremented the API Version"; present in tag v0.8, absent in v0.7): has `ServiceBrowserPrepare(i,i,s,s,u) -> o`, `ServiceResolverPrepare`, then call `org.freedesktop.Avahi.ServiceBrowser.Start()` AFTER subscribing to ItemNew/ItemRemove/Failure/AllForNow/CacheExhausted on the returned path (ServiceBrowser.xml: methods Free, Start). Server2 has no ServiceBrowserNew.
- `ResolveService(i interface, i protocol, s name, s type, s domain, i aprotocol, u flags) -> (i interface, i protocol, s name, s type, s domain, s host, i aprotocol, s address, q port, aay txt, u flags)` on both interfaces.
- Constants (avahi-common/address.h, defs.h): AVAHI_PROTO_INET=0, AVAHI_PROTO_INET6=1, AVAHI_PROTO_UNSPEC=-1, AVAHI_IF_UNSPEC=-1; lookup flags USE_WIDE_AREA=1, USE_MULTICAST=2, NO_TXT=4, NO_ADDRESS=8. Use type "_kintrinsic._tcp", domain "local" (or ""), flags 0.
- Install/enable: Ubuntu 24.04 noble germinate output lists `avahi-daemon | avahi | Ubuntu.Noble desktop-common seed` (directly seeded) https://ubuntu-archive-team.ubuntu.com/germinate-output/ubuntu.noble/desktop-common ; not present in noble `minimal`/`standard`/`desktop-minimal` outputs. Noble ships avahi 0.8-13ubuntu6 (Prepare available). "Enabled by default" is not stated in a doc; observed on this Linux Mint 22.3 box: `systemctl is-enabled avahi-daemon` = enabled, installed 0.8-13ubuntu6.2. Mint-specific seed list: not confirmed. Minimal/server installs: not guaranteed present.
